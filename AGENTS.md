# Made Cms Package

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `made-foryou/made-cms-package`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real. Actions, custom Eloquent Builders, Data objects and the site's strip types (`Content\Strips\StripType`) are the agreed extension points.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.
- Every change a host or editor notices (public API, routes, config, migrations, commands, translations, screens) gets a line under `## [Unreleased]` in `CHANGELOG.md`, in the same change as the code. Use one heading per type in the order Added, Changed, Deprecated, Removed, Fixed, Security; a breaking change says what the host has to do. Internal refactors and tests stay out.

## Architecture Guidelines

- Work test-first: write the failing test in the mirrored `tests/` path, make it pass, then run `composer analyse` and `composer test`.
- `src/` is organised per bounded context (`Access`, `Content`). Technical layers (`Http`, `Console`, `Support`) live outside the contexts.
- A context contains `Actions`, `Builders`, `Data`, `Events`, `Models`, and when needed `Enums`, `Exceptions`, `Listeners`, `Notifications`, `Policies`. `Content` also holds the media library (`Media`, `MediaFolder`) and `Strips` (the strip type definition API, with `Strips/Fields`) and `Scan` (reading rendered HTML for the scan of a site and building the source of the strip types it proposes). Create a folder with its first class, never empty.
- Contexts never import each other and never use `Http`, `Console`, or the service provider. Communicate across contexts through events.
- `Support` holds final, context-free helpers (site name and url, launcher locale, QR code) that contexts and Http may both use; it never uses a context, `Http` or `Console`.
- Actions are the only place for writes and business rules: `final`, `use AsAction`, a typed `handle()`, invoked as `Action::run(...)`. Do not use `asController`, `asListener`, `asJob`, `asCommand` or `rules()`.
- Models only represent a table row: `$table`, `$timestamps`, `$fillable`, `$hidden`, `casts()`, relations, `newEloquentBuilder()` and `newFactory()`. No business logic, no facades. `Editor` also implements Laravel's `Authenticatable` contract through its trait, so the guard can log it in.
- Reads go through custom Eloquent Builders (`Page::query()->published()`), one per model, `final`, suffix `Builder`. No repositories, no ad-hoc queries in Actions or controllers.
- Data objects are `final readonly` plain PHP classes. Events are `final` and `Dispatchable`. Enums are string-backed. Exceptions are `final`.
- Code identifiers are English. UI text is Dutch in `lang/nl` with an English fallback in `lang/en`. Tables use the `cms_` prefix.
- Migrations live in `database/migrations` (`create_cms_*_table`), factories in `database/factories/<Context>/`.
- Do not use Eloquent class attributes such as `#[Table]` or `#[UseEloquentBuilder]`; Laravel 12.0 is still supported.
- The CMS has its own editors (`cms_editors`, `Access\Models\Editor`) and its own session guard (`made-cms-package.auth.guard`, default `made-cms`), registered next to the host's guards. It runs beside the host site and never reads or changes the host's users table, guards or login.
- Editors hold one or more fixed roles (`Access\Enums\Role`, stored in `cms_editors.roles`); `Admin` opens every screen, also screens added later.
- Which role opens which screen lives only in `Role::screens()`. A new CMS screen is a `Screen` case, granted there, with its `ScreenGroup` in `Screen::group()`; the screens of a group follow each other in the cases.
- `docs/rollen-en-schermen.md` explains who opens which screen and why, and marks access that is decided but not built (○). A change to `Role::screens()` updates its matrix in the same change; `tests/Unit/Docs/RolesDocumentTest.php` checks it.
- Every screen has a route `made-cms/<screen>` with `EnsureScreenAccess::using(Screen::X)`. Until it is built, the loop in the routes file sends it to `UpcomingScreenController`; a built screen leaves the loop and gets its own controller.
- Menus and dashboards list `ListScreens::run($editor)`, grouped by `Screen::group()` (`Http\Cms\Menu`); hiding a menu item is UI only, the route middleware is the authorisation.
- The start page (`made-cms/start`) opens for every logged-in editor (`EnsureEditor`). Its blocks are static design samples in `Http\Cms\StartPageSample` until the contexts deliver them; a sample item never links to a screen the editor does not open.
- Roles change only through `AssignRoles`: the editor making the change needs the `Editors` screen, only an admin gives or takes `Admin`, the last admin keeps it, and every editor has at least one role.
- `Content` never checks roles; screen access is enforced at the Http boundary.
- Editors build pages from strip types the site defines: one class per type in `app/Cms/Strips` (`made-cms-package.strips.path`/`namespace`) extending the abstract `StripType`, with a fixed `key()` that is stored with the content and never derived from the class name. `StripTypes` is the catalogue (a singleton bound in the service provider) and checks every definition when it is built; a broken definition is a developer error and throws.
- Strip definitions only describe: `StripType` and the immutable fields in `Content\Strips\Fields` (`final`, every setter returns a changed copy) derive validation rules, labels, defaults, normalised values and summaries, but never write, dispatch events or use facades. Actions validate and store strip content with them, always through `CheckStripValues` (a missing field as its default, the values in their stored form).
- A field has a stored form (`normalize()`) and a rendered form (`render()`, e.g. a link as its url). `StripType::render()` renders every field, fills a missing one from its default and puts `with()` on top of the rendered values.
- A stored value is read in its current form (`$type->normalize()`) before it is checked again (`UpdateStrip`, `PublishPage`, `RestoreStrip`) or compared (`CompareDraft`), as `DescribeStrip` hands it to the panel: a value a former field type stored (a `Text` that became a `Heading`) or a choice the definition no longer offers never stops a publication. Values an editor sends are checked as they come.
- A heading is a `Heading` field, stored and rendered as `{text, tag}` (`h1`–`h6` or `span`; a text stored before is the text at the default level, an empty one at the default level is `null`). The site prints the tag from the value (`<x-made-cms::heading>` in Blade) and styles it by class, never by tag.
- Only an editor who opens `Screen::MetaTags` chooses the level of a heading. Http decides it once (`Visitor::choosesHeadingLevels()`) and hands it to `UpdateStrip`/`RestoreStrip` as `chooseLevels` (no default); without it they keep the stored level through `StripType::keepLevels()` (also in a list by item id; `RestoreStrip` takes the published strip, else the default). The panel gets it as `config.heading_levels`, only UI.
- `RichText::render()` cleans the HTML again as its last step (also once #79 sets `href`), so content that skipped `normalize()` (a seeder, an import, a former field type, a default) never reaches a visitor or the edit frame raw. It parses through `Content\Strips\RichTextParser`, which unwraps markup deeper than 100 levels (the sanitizer recurses) and drops `//host` addresses.
- Rendering trusts no stored value: `Link::resolve()` gives only an address `Link`'s validation accepts, and `DescribeStrip` hands the panel normalized values. In the shell `panel.js` sends `edit.js` rich text only as `richHtml()` builds it and links only as `ADDRESS` accepts them.
- Visitors get strips only through `RenderStrips::run($page)` (`Content\Data\RenderedStrips`): published (the working copy in the edit mode), visible, in order, catalogue types only, as `{id, type, ...fields}`. Never hand `$page->strips` to a view or prop.
- Blade components for the site live in `Http\Components` under the component namespace `made-cms`. `<x-made-cms::strips>` renders `strips.{key}` or `view()` with `$strip` and throws `MissingStripView` before rendering when a view is missing. `<x-made-cms::heading>` prints a heading as the element of its level (a tag outside `Heading::TAGS` as `span`) with `data-cms-field` and the site's attributes, and nothing without a text.
- The site's strip views set `data-cms-strip` (required) and `data-cms-field`/`data-cms-items` (optional); the package only promises the id.
- A page holds its published strips in `cms_pages.strips` and a nullable draft in `draft_strips` (stored as `{id, type, visible, values}`, read through `Content\Data\PageStrips`). Every strip write goes to the draft through a Content Action; `PublishPage` validates the draft and makes it the published version. A strip whose type left the catalogue keeps its data.
- Every change of the draft (the strip Actions, `PublishPage`, `DiscardDraft`) runs through `ChangeDraft`: in a transaction it reads the page again with its row locked (`lockForUpdate`), gives the change the working copy and the page, and saves. Changes at the same time follow each other, and the page from the route never writes an old draft back. Never read the working copy for a write, or write `draft_strips`, outside its closure.
- `draft_strips !== null` means the draft changes something: after every change `ChangeDraft` asks `CompareDraft` and drops a draft without changes, so overviews and counts can rely on the column. An empty draft (`[]`) of a published page with strips is a change, not "no draft".
- Content events implement `ShouldDispatchAfterCommit` (`tests/Arch/DomainObjectsTest.php`), so an Action may dispatch inside its transaction: listeners run after the commit, also of a transaction of the host.
- `CompareDraft` is the only place that says what a draft changes (`DraftChanges`) and whether it can be published or discarded: each strip counts once (added, removed, changed fields or visibility, moved), values in their stored form (`normalize()`, missing field = default), without key order or item ids.
- Every address of the site is a row in `cms_routes` (`Content\Models\Route`): a unique, normalised `path` (`Content\Data\PagePath`, `/` for home) and a polymorphic `routable` (pages as `cms_page`). New content with an address points its own row there; never store a path on the content table. A draft page keeps its address.
- The site serves pages with `Route::madeCms($responder)` (`Http\Routing\RouterMixin`): a nameless `{path?}` catch-all whose `ResolvePage` middleware runs `FindPublishedPage` and swaps the `path` parameter for the page. Visitors never see a draft.
- The edit mode is the site in the frame of the CMS: `?made-cms=edit` plus an editor who opens `Screen::Pages` (`CheckScreenAccess`). `ResolvePage` then finds the page with `FindPage` (any status), switches the scoped `Content\Data\EditMode` on (back off in `terminate()`, never in `handle()`, because `InjectLauncher` reads it afterwards) and sends `no-store`, `X-Frame-Options: SAMEORIGIN` and `noindex`. `RenderStrips` renders the working copy in it and `ShowLauncher` hides the launcher. Anyone else gets the visitor's answer: a draft stays 404, never 403.
- `?made-cms=preview` is the same mode outside the frame ("Voorvertoning" in a tab of its own); `EditMode` stays one flag, so frame-only behaviour belongs in `edit.js`, not in the mode.
- Pages form a tree (`parent_id`, `position` among siblings, `in_menu`). The address of a page is its parent's address plus its slug (`/` + slug at the top and under the home page). Only the Content Actions (`CreatePage`, `UpdatePage`, `MovePage`, `DeletePage`, `RestorePage`) change the tree, and they rewrite the addresses of the pages below in the same transaction. The home page (route `/`) keeps its address, stays at the top and is never deleted.
- Deleting a page is a soft delete that frees its `cms_routes` row; `made-cms:prune` (scheduled daily by the package) removes it after `pages.keep_deleted_days`.
- CMS screens with input use plain HTML forms (`@csrf`, `@method`), no JSON, except the edit shell (side panel, opbouw and bar): a form post would reload the shell and the site in its frame. A refusal goes back to the form with `$request->reject()`; a success redirects through a Response class (`PageRedirect`) with a flash notice that `Shell` shows on the next page.
- The edit shell (`made-cms/pages/{page}/edit`, `EditPageResponse`, `cms/edit.blade.php`, `edit.js`) frames the page in the edit mode. `edit.js` outlines every `[data-cms-strip]` from a shadow root of its own element in the frame, keeps the chosen strip across reloads and blocks links and forms there; the only change it makes to the site is patching `[data-cms-field]` elements. Strip names and texts reach it as JSON (`data-config`) from `ListEditableStrips` and `lang/`.
- Adding a context: add it to `contexts()` in `tests/Pest.php` and start with one Model and one Action, both tested.
- Arch tests in `tests/Arch/` enforce these rules; a failing arch test means the code is wrong, not the test.
- Decisions are business rules too, even without a write (e.g. who sees the launcher): put them in a context Action with a Data object as input. Http only translates the request into that Data.
- Controllers stay as empty as possible: a FormRequest in `src/Http/Requests/<Context>/` (final, suffix `Request`, extends `LauncherRequest`) validates, holds the translated messages and turns the input into context Data with `toData()`; the controller runs one Action and returns a Response class from `src/Http/Responses/`. A rejection by an Action becomes a field error through `$request->reject($field, $error)`; controllers never validate or build messages themselves.
- The side panel (`panel.js`) builds its controls from `StripType::describe()` (`DescribeStrip`, `GET made-cms/pages/{page}/strips/{strip}`) and saves with fetch + JSON (`X-CSRF-TOKEN` from `data-config`): always every field to `UpdateStrip`, visibility to `SetStripVisibility`. A refusal is the 422 of the Action's `ValidationException`, keyed by field path. Fixed texts live in the `<template>`s of `cms/edit.blade.php`, the texts it fills in in `cms.edit.panel_texts`; `edit.js` and `panel.js` talk through `made-cms:select`, `made-cms:input`, `made-cms:saved` and `made-cms:visibility` events on `[data-edit-shell]`.
- Watching along: `panel.js` sends every change as `made-cms:input` `{id, path, type, value, count, seq}` with the value as the strip renders it (`rendered()`, like `Field::render()`); `edit.js` patches it into the `[data-cms-field]` elements (in `[data-cms-items]` the direct children are the items, a field in it is relative to the item). What it cannot patch (no element, empty value, choice, a list changing, visibility) marks the strip stale up to that `seq`, and the `made-cms:saved {id, seq}` that stores it reloads the frame. Unsaved changes are patched again after every reload.
- A patch changes only the single text node (`nodeValue`), `href` or the HTML of rich text, never `textContent` or the element itself, so React and Vue keep it; an element that holds more than its text is not patched. A long text follows the form the site prints it in (`<br>` or line breaks in the text). A heading patches its text only while `node.localName` is its `tag`; another level reloads the frame.
- A click on an outline opens the field under the pointer (`elementsFromPoint`) through `made-cms:select {id, field, count}`; the tab with the name and the keyboard choose the strip only.
- A new field type adds its `type()` and `details()` for `describe()`, a `<template data-field="…">` in `cms/edit.blade.php` and its control in `panel.js`.
- The bar (`bar.js`) shows the state of `GET …/pages/{page}/draft` (`DraftResponse`, texts and plurals made on the server), publishes with `POST …/publish` and discards with `DELETE …/draft`; both answer 204 and the bar asks for the state again. Its slots are named `bar-*`, because the panel takes the first `[data-slot]` of the shell.
- Before publishing the bar waits for the panel to save what it holds (`made-cms:flush`), before discarding for it to stop saving (`made-cms:discarding`); after publishing the frame reloads (`made-cms:published`), after discarding the whole shell. A strip that stops the publication is chosen with its errors (`made-cms:choose` → `made-cms:select`).
- "Ongedaan maken" is session state of the panel: each strip keeps what the server stored before every save and a step back saves it again through `UpdateStrip`/`SetStripVisibility`; there is no undo on the server.
- The opbouw (`structure.js`) is the start of the side panel. It lists every strip of the working copy in stored order (`ListEditableStrips`, also hidden strips and strips whose type left the catalogue as `known: false`), so the place of a strip in it is the position the strip Actions take and the number "Strook n van m" shows everywhere, on the outlines too. It adds (`AddStrip`, catalogue from `config.types`), moves (`MoveStrip`, one request per drop) and removes (`RemoveStrip`) through the `…/strips` endpoints, which answer the whole list with its counts (`PageStripsResponse`, plurals made on the server); `GET …/strips` gives the list again after the panel saved.
- After every change of the opbouw `structure.js` sends `made-cms:strips {strips, counts, reload, reveal}`: `edit.js` takes the labels and places and reloads the frame, `bar.js` asks for the draft again, `panel.js` forgets a strip that left the page. Before removing a strip it waits for the panel to save it (`made-cms:removing`). `made-cms:choose {id: null}` goes back to the opbouw, `{id, added}` chooses a strip it just added; its slots are `head-*`, `structure-*`, `catalogue-*` and `row-*`.
- Undoing a removal is session state of the opbouw too: the `DELETE` answer holds the strip as stored and `RestoreStrip` puts it back with its own id, so `CompareDraft` counts nothing for it; a strip whose type left the catalogue comes back only as the published page holds it.
- A strip in a list of the CMS (the opbouw, later "Wat erop staat" and the link picker) is summed up by `StripType::summary()`: the first field with text (`Field::summary()`), else the titles of the items of a list.
- The overview "Koppen" is a tab next to the opbouw for whoever opens `Screen::MetaTags` (`config.heading_levels`, only UI; `structure.js` owns the tabs `head-tab*` and the view, `headings.js` the slots `headings-*`). Only the frame knows the headings: `edit.js` reads every h1–h6 in document order plus the element of a `Heading` field at "Geen kop" (never a span of the site), after every scan, patch and `made-cms:view {view: 'headings'}`, and sends `made-cms:headings {headings}` with `{tag, text, strip, field, count, heading, list, visible}` when they changed.
- Which fields are a heading comes from the server (`StripType::headings()`, `headings` per strip in `config.strips` and `made-cms:strips`). A heading of a field opens it through `made-cms:choose {id, field, count}`; "no strip" goes back to the tab the editor came from, except after removing a strip (back to the opbouw, where "Ongedaan maken" is). The signals (no H1, more than one H1, skipped level, empty heading) count every h1–h6, also one hidden with css; their texts live in `cms.edit.headings_texts`.
- The scan machinery reads a rendered site and builds code, but never writes: no writes, events, models or facades in `Content\Scan` (`tests/Arch/ScanTest.php`, `tests/Arch/WritingTest.php`), only the markup through `Dom\HTMLDocument`, never computed styles, and deterministic without any service.
- `RecognisePage` reads one page (`ScannedPage` with the browser's `outerHTML`) into a `RecognisedPage`: raw facts per strip (fingerprint, hint, selector, fields by `ScanRole`), which wait between requests through `toArray()`/`fromArray()`. `CombinePageScans` turns all pages into the `ScanResult` and is the only place for what needs every instance: types by fingerprint, static design text, icon choices, the level of a heading, `required`, `max` and the names.
- The level of a heading is content to the scan, never structure: the fingerprint and `ItemGroups` see every h1–h6 as one heading, `TypeMerger` lines a heading up by its place among the headings of its parent (not by its selector), and a heading's value is `{text, tag}`. Its default `tag` is the level most examples have (the highest on a tie), with `heading_levels_differ` when they differ.
- `ScanResult` is the one form the later steps of the scan (review, definitions, views, import, AI) build on. `docs/scanresultaat.md` describes it and changes with it; `tests/Unit/Docs/ScanResultDocumentTest.php` checks its example and doubts.
- Scan selectors are steps `tag` / `tag:nth-of-type(n)` joined by ` > `, from the strip (or item) root; `document.querySelector(strip + ' > ' + field)` finds the element in PHP and the browser (PHP's DOM has no `:scope`).
- `ScannedStripType` is the one mapping from a `ScanType` to the field API, so the catalogue checks a proposal before it is written: images wait for the image field and are left out (`leftOut()`), a list gets `max` but `min` only above 1, the options of a choice get a label, a heading is a `Heading` at its scanned level. `StripTypeSource` prints it as the class the developer would write (the style of the TTV stubs: no `declare`, `label()` only when the class name does not read as it, `->tag()` only when the level is not the default h2) and its output passes Pint unchanged.
- `GenerateStripTypes` is the only code that writes files into the site (`tests/Arch/WritingTest.php`): a class per type of a (reviewed) `ScanResult` in `strips.path` under `strips.namespace`, only at `APP_ENV=local` (`NotLocalEnvironment`), created with `fopen` mode `x`. It never overwrites and skips (`StripTypeSkip`), in this order, a type the catalogue would refuse (`invalid`), a key the catalogue or the scan already has (`key_exists`) and a class the folder already has, whatever its capitals (`class_exists`).
- The scan endpoints (`made-cms/scan/*`) open only for an admin at `APP_ENV=local`: `EnsureScanAccess` runs `CheckScanAccess`, whatever the panel shows. The scan has no `Screen` case.
- Media belongs to `Content`, not to a context of its own: `Content\Models\Media` (`cms_media`) and `MediaFolder` (`cms_media_folders`, one level deep), their Actions in `Content\Actions`. A strip stores the id of a file, so a file changes everywhere it is used; its alt text belongs to the file, not to the place.
- Files reach the media disk (`media.disk`) only through the Content Actions, through `Storage` and never `fopen` (`tests/Arch/WritingTest.php`). `CheckMediaDisk` runs when the library is first used, never while the app boots, and refuses a disk a visitor cannot open (a local disk without `url`).
- `UploadMedia::run(UploadedMedia)` takes a local path and the name as the editor had it, never an `UploadedFile` (Actions take no `Illuminate\Http`). `CheckUploadedMedia` reads the type from the contents (`finfo`), never from the name, checks size, then type, then the svg, and refuses with a `ValidationException` keyed by `file` and a message from `lang/`.
- Every file gets a folder `media/{ulid}` of its own. A photo is scaled down by `ScaleImage` (`intervention/image` ^4, upright, without camera metadata, at most `media.image.max_width`, never larger) to `{name}.{format}`; the upload stays next to it as `original-{40 random characters}.{ext}`, so nobody guesses its url from the photo's. An svg, an animated gif, a document and a video are stored as they came in.
- An svg is stored as it came in only when it does nothing but draw (`CheckSvg`): no script, `foreignObject`, html, event attribute, processing instruction, entity, reference outside the drawing (a photo may be a `data:image/…` url) or style that loads something.
- An image in a strip is an `Image` field, stored as the id of a file (`normalize()` gives an int, anything else is no image) and rendered as `{url, alt, width, height, focal}`, `alt` always a text. It has no `default()`, also not in the default of a list (the catalogue refuses both). A file that is gone or is no image renders as `null`, never an exception; `rules()` refuses it, so saving and publishing stop on it.
- `Field::places()` / `StripType::places()` is the one place that says which files a stored value holds, by the path of their place (`foto`, `kaarten.{id}.foto`: an item by its id, so a place survives a move; an item stored without an id by its position); `media()` (the ids, each once) follows from it and is final. A field type that holds files (an image, later a file or a link to one) overrides `places()`. The url of a file comes only from `FindMedia` (through `CheckMediaDisk`, one query, nothing asked without ids): `RenderStrips` and `DescribeStrip` run it once and hand the files to `render()` as `MediaFiles`; a field never looks a file up for rendering. Nothing a visitor or the panel gets holds `path` or `original_path`.
- Where a file is used lives in `cms_media_usages` (`MediaUsage`): one row per place, by page, version (`UsageVersion`: `published` for `strips`, `draft` for `draft_strips` while there is one), strip, the key of its type and the path of its field. Only `SyncMediaUsage` writes it, from `ChangeDraft` (in its transaction, when `strips` or `draft_strips` changed) and `RebuildMediaUsage` (`made-cms:media-usage`, each page with its row locked); it writes only the difference. Package code that writes `strips` or `draft_strips` outside `ChangeDraft` (duplicating a page in #68, the import of the scan in #33) runs `SyncMediaUsage` for that page in the same transaction; the command is for content the package did not write. An id without a file gets no row. For a strip whose type left the catalogue the rows of either version say which paths are files, and each holds the id its values in this version hold there (publishing its draft moves the file along).
- A file is in use while any row points at it, in either version, also of a hidden strip or of a deleted page until it is pruned (`cms_pages` cascades, `cms_media` restricts). `MediaBuilder::inUse()` and `withUsage()` read it; `MediaUsage::page()` includes deleted pages. `ListMediaPlaces` names a place from the catalogue (`StripType::placeLabels($path, $values)`: "Hero › Achtergrondfoto", "Fotorij › Foto 3 › Afbeelding", the number from the values of the version the place is in) at the moment it is shown, never a stored text, and by its keys when the catalogue cannot name it.
- The panel gets the images of a strip as `strip.media` (`StripResponse`, `{id, url, name, extension, meta, folder, alt, image}`) next to the values in stored form; `panel.js` keeps them by id like `pages`, and `rendered()` of an image is its `image`. `edit.js` patches only a plain `<img>` (`src`, `alt`, and `width`/`height` when the site prints them); anything else reloads.
- Editors upload through one upload field, the same in the media library, the picker and the edit shell: the partial `cms/partials/upload.blade.php` with `UploadField::make($folder)` (`Http\Cms`), or `UploadField::image($folder)` for an image (one photo at a time, only image types, singular texts from `media.upload.single`), and `upload.js`, a file of its own because the edit shell does not load `cms.js`. A host includes the partial and loads `$upload['script']`; never build a second upload control.
- `upload.js` starts every `[data-upload]` that is on the page, also one a script puts there later (a `MutationObserver`, each field once), so a host never starts a field itself.
- The field gets its config as JSON on itself (`data-config`, not the `script[data-config]` of the shell), so a page can hold more than one field; its fixed texts are in the partial, the ones `upload.js` fills in in `media.upload.texts`. Its slots are named `upload-*`, its rows come from the `<template data-upload-row>` inside it.
- `upload.js` sends files one at a time (`POST made-cms/media`, one file per request, XHR for the progress), so the server never scales several photos at once. An error belongs to its file and stays until the editor leaves it out or tries again; the others go on. It saves alt texts with `PUT made-cms/media/{media}/alt`, one request per file.
- The field tells its host what happens through bubbling events on `[data-upload]`: `made-cms:upload {busy, done, total, failed, percent, sending}` (also while a file travels), `made-cms:uploaded {file}` and `made-cms:upload-closed {files}`. A host listens, and stops what is on its way with `made-cms:upload-stop` on the field (only while `sending`: a file the server stores lands in the library); it never reaches into the rows of the field.
- A host sends a field into another folder with `made-cms:upload-folder {folder: {id, name} | null}` on the field, also a field it just put on the page (a capture listener of `upload.js` starts it first). A file keeps the folder it came in with (`row.folder`), so a waiting or retried file never moves into a folder chosen later; the line "komt in …" comes from `texts.rules` with `:folder` open.
- What the library takes is said in one place, `DescribeUploadLimits` (`UploadLimits`): `CheckUploadedMedia` refuses with it and `UploadField` tells the editor with it. The size check in `upload.js` only spares an upload; `UploadMediaRequest` checks that one file arrived and nothing about its type or size, because the Action reads the contents.
- An upload php itself refused (`upload_max_filesize`, `post_max_size`, a 413) is the server's limit, not the library's: it gets `media.errors.server_limit` with `UploadField::serverLimit()`, never "mag 25 MB zijn".
- A file for the CMS is shown through `Http\Cms\MediaDetails` (`{id, url, name, extension, meta, folder, alt, image}`; `extension` is the type of the file a visitor gets, `webp` for a scaled photo), in the side panel (`StripResponse`) and in the answers of the media endpoints (`MediaResponse`, plus `kind`, `file` and `size`). The original size of a photo is not stored; the field says "was 4,2 MB" from the file the browser held.
- Uploading, saving an alt text and listing the library for the picker open for an editor who opens `Screen::Pages` or `Screen::Media`: `EnsureScreenAccess::using(Screen::Pages, Screen::Media)` lets an editor through who opens one of the screens. Use more than one screen only for an action that stands on more than one screen.
- The media element is the control of an `Image` field in the side panel (`<template data-field="image">`, design 13.2/13.3): it shows the file from `strip.media` (a file without `image` counts as gone) and uploads through the field of `UploadField::image()`, cloned from `<template data-part="upload">`. The photo is the value of the field on `made-cms:uploaded`; its alt text follows on `made-cms:upload-closed`. "Kiezen uit media" (`image-pick`) opens the picker; its choice reaches the field through `where()`, like an upload, and an upload of that field still on its way is `superseded` and lands in Media only.
- The picker (design 13.4/14.4) is a native `<dialog>` with `showModal()` (`cms/partials/media-picker.blade.php`, `MediaBrowser::picker()`), inside `[data-edit-shell]` after the `.bewerkromp`, so its events reach the shell and the panel, which takes the first slot of a name in the shell, finds its own slots first. Its slots are named `media-*` and `media-picker-*`. The panel opens it with `made-cms:pick {field, place, hint, file, opener, choose(file)}` on the dialog; it never reaches into it.
- The list of the library (`[data-media]`, `cms/partials/media-browser.blade.php`, `MediaBrowser::make()`, `media.js`) is one for the picker and the media library: its folder and tile are `<template data-media-folder>` and `<template data-media-tile>` in the partial, never a second markup. It reads `GET made-cms/media/files` (`ListMedia`, 40 a time, `MediaResponse::listed()`) and `GET made-cms/media/folders` (`ListMediaFolders`), never `made-cms/media`, which is the screen. It tells `made-cms:media-chosen {file}` and `made-cms:media-folder {folder}`; `made-cms:media-load {file}` loads it again.
- The picker shows only what the field takes (`kind`, images for an `Image`): no grey tiles for other kinds, and the folders count that kind.
- The folder an editor opens in the picker is remembered for the session (`PUT made-cms/media/chosen-folder`, `Http\Session\MediaFolderMemory`): the side panel follows it at once (`config.folder`, `made-cms:media-folder` → `made-cms:upload-folder` on its fields) and the next shell starts there (`FindMediaFolder`, a folder that is gone is "Alle bestanden"). The session is written back whole after every request, so `media.js` sends it only once the list of that folder is in and the dialog is open; an overlapping request can still bring back the former folder, which is accepted.
- The panel keeps every upload it opened (`uploads` in `panel.js`) apart from its controls: `render()` hangs its field in again, and a photo that comes in goes to its field where it is now (`where()`: the values of the strip, or its item by object, else by id); a strip or an item that is gone gets nothing. `flush()` waits for uploads on their way, so publishing takes the photo.
- The field of one photo folds down in the panel by css on `[data-one-image]` and `data-moment` (design 13.2b): only its row while busy, only the alt text when done, a refusal above the zone; the panel's part adds the hint while busy and "Annuleren" (rest, error and while `sending`).
- The line at the foot of the side panel (`[data-slot="upload-status"]`, outside the form, design 13.2c) belongs to the panel: it names the place of an upload as "Hero › Foto" or "Kaarten › Kaart 2 › Icoon", reads out only its text (`role="status"` on the text, the percent `aria-hidden`), and shows a result only when it happened out of sight: a failure until the editor opens that field ("Open dat veld" goes through `made-cms:choose {id, field, count}`) or closes it, a photo that came in until the next `made-cms:select` or its cross. No timer takes a message away.
- A component that is not on a screen yet (the upload field with several files until #55) is shown on a page of the workbench (`workbench/routes/web.php`, above `Route::madeCms()`), where its browser test runs.
- `.sr-only` wins with `!important`, so a visually hidden element stays hidden among the styles of a field around it (`.paneel .veld input`).
- An svg element has no `hidden` property: hide one with `toggleAttribute('hidden', …)`.
- Http middleware the host must get without configuration is appended to the kernel's `web` group via `callAfterResolving(Kernel)`, never pushed onto the router (that is lost when the kernel re-syncs its groups).
- The launcher (Blade markup under the `made-cms-package-launcher` view namespace, css, js, fonts) lives in `resources/launcher/`, is never published, and its static assets are served by a whitelisted controller in a route group without middleware; hosts never publish them.
- CMS pages (start page, screens) render in the shell `resources/launcher/cms/` (`Http\Cms\Shell`, one Response class per page) with `cms.css` and `cms.js`, served by the same whitelisted controller. They are plain documents without a shadow root, follow `prefers-color-scheme`, and are sent `no-store`, `DENY` and `noindex`.
- The launcher's visibility is UI only and never authorisation.
- Login endpoints answer `{step, data, csrf_token}` (`StepResponse`); the server decides the next step and the JSON carries data only. All copy lives in `lang/` and the launcher's step templates, never in JS or JSON.
- Never reveal whether an address has an account: same answer, same message and (with `Timebox`) same time for unknown addresses. Every path of a password login checks exactly one hash (a stand-in from the cache when there is no real one), and login codes are HMACs, so no path does more hashing than another.
- Rate limits key on what was typed and the network, never on whether an account exists: the typed address with the network, the network alone, and the typed address alone (across ip addresses), where a browser whose device cookie knows the address counts on its own. The network is the IPv4 address or the IPv6 /64. Only after a right password may a limit key on the editor, also without the network (the second factor). One message for every limit.
- A new login code replaces only the code of the same browser (`session_hash`); codes of other browsers keep working.
- Secrets (login codes, link tokens, TOTP secrets) are stored hashed (login codes as an HMAC with the app key) or encrypted and only travel in memory; events and notifications that carry them are handled synchronously and never queued.
