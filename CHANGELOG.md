# Release Notes

## [Unreleased](https://github.com/made-foryou/made-cms-package/compare/v0.1.0...1.x)

### Added

- A photo uploaded in the picker goes to the crop step once it is in, which asks its name and alt text instead of the upload field; an svg and an animated gif keep the alt text in the field. A screen gives an upload field the same with `UploadField::make($folder, crop: true)` or `UploadField::image($folder, crop: true)` and the crop step on the page: the photos of a batch go to the step one after the other once the batch is in, while the editor still sees the field, and the field asks the alt text of a photo the editor did not get to there, of one that came in after its dialog closed and of one the step did not take.
- "Bijsnijden" in the media element of the side panel opens the crop step for the photo of the field (only for a photo with an original to cut from, not for an svg or an animated gif). The field keeps the id of the file, so the draft does not change: the media element shows the new crop at once and the frame reloads, because the file changed on every page that shows it.
- The crop step (design 13.6, 14.6): a modal dialog in the edit shell that gets a photo ready for the site, one file after the other. The whole original on a dark stage with the frame of the crop (drag it, pull a corner), the ratios Vrij, 16:9, 4:3, 3:2, 1:1 and Origineel, turning left and right, mirroring, "Herstel" and the focal point; the frame, its corners and the focal point move with the arrow keys too. On the right "Verkleinen voor het web" with the size of the original and an estimate of the photo ("4,2 MB jpg / ± 380 kB WebP"), the file name, the alt text and, for an editor who opens the media library, the folder. "Opslaan" stores what changed and goes to the next file; "Zo laten, zonder snijden", the cross and Escape store the fields on the right and leave the photo. A photo on a page says how many pages a crop changes. A screen includes it with the partial `cms.partials.crop` and `['crop' => CropStep::make($moves)]`, loads `$crop['script']` (`crop.js`) and opens it with `made-cms:crop` `{files, opener, upload, done(results)}` on the dialog, which sets `taken` on the detail when the step opens for the files; it tells `made-cms:media-changed` `{file}` for every file it stored. Dutch and English texts in `media.crop.*`.
- `PUT made-cms/media/{media}/name` renames a file through `RenameMedia`, for an editor who opens the pages or the media library, and `PUT made-cms/media/{media}/move` puts it into a folder through `MoveMedia`, only for an editor who opens the media library.
- Endpoints for the crop step, open for an editor who opens the pages or the media library: `GET made-cms/media/{media}/crop` describes a photo (its original, its crop, the line under the title and on how many pages a crop changes it), `GET made-cms/media/{media}/original` shows its whole original upright, scaled down and without metadata (only through this route, never stored by a cache) and `POST made-cms/media/{media}/crop` cuts it through `CropImage`. Dutch and English texts in `media.crop.*` and `media.errors.*`.
- `DescribeMediaCrop::run($media)` gives a photo as the crop step shows it (`MediaCrop`): the file, the upright size, bytes and extension of its original, how it was cut from it (the whole original when it never was) and the number of pages that show it, without the deleted ones (`MediaPlaces::pageCount(withDeleted: false)`). `MakeOriginalPreview::run($media)` gives the whole original upright, scaled down and without the metadata of the camera, made for each request and never stored; `DecodeOriginal::run($media)` reads the original upright. They throw `MediaNotCroppable` for a file without an original.
- `RenameMedia::run($media, $name)` gives a file of the library another name: the typed name as a slug (`MediaName`), the name search engines read. The file the site shows moves to it in its own folder, so it gets another address that every page takes at once; the former address stops working after the commit. A name without letters or digits is refused with a `ValidationException` keyed by `name`. `MoveMedia::run($media, $folderId)` puts a file into a folder, or into none for `null` (throws `MediaFolderNotFound`); its address stays. They dispatch `MediaRenamed` and `MediaMoved` after the commit.
- `CropImage::run($media, new CropMedia(new CropArea($x, $y, $width, $height, $rotation, $flip), $focalX, $focalY, $scaleDown))` cuts a photo from its original again: the area in pixels of the original as the editor sees it (upright, turned clockwise by 0, 90, 180 or 270 degrees, then mirrored left to right when `$flip`), scaled down to `media.image.max_width` unless `$scaleDown` is off (then it keeps its size, still as `media.image.format`), with the focal point from 0 to 1 of the photo that comes out. The original stays, so the next crop starts from it again. The photo gets a new address in a folder of its own next to the original (`media/{ulid}/{random}/{name}.webp`) and a new thumbnail, so no cache keeps the former photo; the former files leave the disk after the commit. When only the focal point changes, no file is written. It changes the photo on every page that shows it, the published version too. An area outside the photo, or an original that cannot be read, is refused with a `ValidationException` keyed by `crop`; a file without an original (an svg, an animated gif, a document, a video) throws `MediaNotCroppable`. It dispatches `MediaCropped` after the commit. `cms_media` keeps the crop in the column `crop` (json, null for the whole original) so the next crop starts where the editor left off. A host that already ran the `cms_media` migration publishes the migrations again and runs `migrate:fresh`.
- `cms_media` keeps the upright size of the original of a photo that was scaled down in `original_width` and `original_height` (null for a file kept as it came in), the image a crop is cut from. `ScaledImage` tells it as `sourceWidth` and `sourceHeight`. A host that already ran the `cms_media` migration publishes the migrations again and runs `migrate:fresh`.
- `ListMenuPages::run()` gives the menu of the site as a `PageTree`: the published pages with "Staat in het menu" on, in the order of the pages screen. A draft or a page outside the menu is left out with the pages under it, a deleted page never shows. Build the menu of the site from it (`->roots` for a menu of one level) instead of `ListPages::run()->inMenu()`, which keeps drafts.
- `PageTree::published()` keeps only the published pages of a tree; a draft takes the pages under it along. `PageTree::inMenu()` follows only the menu switch and keeps drafts: it is the tree of the CMS, not the menu of the site.
- A photo gets a thumbnail when it is uploaded, for the tiles of the CMS: the photo as the site shows it, scaled down until it just covers 480 × 360 (never up, never cropped), stored as `thumb-{random}.webp` in the folder of the file and in the column `thumb_path` of `cms_media`. An svg, an animated gif, a pdf and an mp4 get none. `MakeThumbnail::run($photo)` makes one from the contents of a photo; `MediaBuilder::scaled()` gives the photos that were scaled down and `withoutThumbnail()` those of them without a thumbnail. The choice of `media.image.driver` is the enum `ImageDriver` (`gd`, `imagick`).
- A file of the media library as the CMS shows it (`file` of the media endpoints and `strip.media` of `GET /made-cms/pages/{page}/strips/{strip}`) holds its `thumb`: the url to show it small at, the thumbnail of a photo, an image without one (an svg, an animated gif) itself and `null` for a document or a video; never the original. `MediaFile::$thumb` gives the same; a strip still renders the photo itself.
- Artisan command `made-cms:media-thumbnails` (`MakeMissingThumbnails`, `MadeThumbnails`) gives every photo that was scaled down but has no thumbnail one, from the photo the site shows, and says how many it made and how many photos had one already. A site with photos from before the thumbnails runs it once. A photo whose file is not on the media disk or cannot be read is named and the others go on; the command then fails. Dutch and English texts in `console.media_thumbnails.*`.

- `POST /made-cms/media` (`made-cms-package.media.store`) takes one file into the media library: a multipart request with `file` and, when the file goes into a folder, `folder` (the id of a media folder). - Field type `Heading` (`Content\Strips\Fields\Heading`, `heading` in `describe()`): a text with its level, stored and rendered as `{"text": "…", "tag": "h2"}`. The level is `h1` to `h6`, or `span` for a text that is no heading for search engines. `Heading::make('kop')->tag('h1')` gives the level of the design (`h2` by default) and `->tags(['h1', 'h2'])` limits the levels to choose from (all seven by default). The text follows the rules of a `Text`; a level outside `tags()` is refused. A text stored before the field became a `Heading` (a former `Text`) counts as that text with the default level, so switching needs no migration: `UpdateStrip`, `PublishPage` and `RestoreStrip` check a stored value in its current form and `CompareDraft` counts no change for it. A level the developer later takes out of `tags()` counts as the default level too, so it never stops a publication. ### Changed

- A search in the media library (`q` of `GET /made-cms/media/files`, `MediaBuilder::search()`, the picker) also finds a file by the title of a page it is used on, in the draft or the published version of the page, never a deleted one. The search field says "Zoek op naam, alt-tekst of pagina".
- The README asks for a `memory_limit` of at least 256 MB instead of 128 MB: with GD, cropping a phone photo of 12 MP takes about 140 MB and one of 24 MP up to about 290 MB. A cropped photo is scaled down before it turns, so turning never copies the whole cut.
- A file as the CMS shows it (`file` of the media endpoints, `strip.media` of the side panel, `MediaDetails`) has `croppable`: whether it is a photo with an original to cut it from again. `MediaFile` has it too, from `FindMedia`.
- The hint under "Staat in het menu" on the screen of one page counts only the pages the site shows in its menu (`ListMenuPages`): "Plek 2 van 3 in het menu." no longer counts drafts. A draft says the place it takes once published ("Komt op plek 3 van 4 in het menu zodra je hem publiceert."), and a page under a page the menu of the site leaves out names that page ("Komt in het menu zodra Over ons erin staat."). Dutch and English texts `pages.show.in_menu.publish` and `pages.show.in_menu.parent`; `ShowPageResponse::make()` takes the menu of the site as its last argument.
- The tiles of the picker, the choice at its foot and the row of a photo in the upload field load the thumbnail of a photo (`thumb`) instead of the photo the site shows, so a page of 40 tiles loads a few dozen kB per photo. The media element of the side panel still shows the photo itself.
- The media element of the side panel offers "Kiezen uit media" next to "Uploaden", and the text for a file that left Media points to both. A photo uploaded from the side panel goes into the folder the editor opened last in the picker instead of always into "Alle bestanden".
- `EditPageResponse::make()` takes the folder the editor chose last as its last argument (`?MediaFolder $folder`, null for "Alle bestanden").
- `Field::render($value, ?MediaFiles $media = null)` and `StripType::render($values, ?MediaFiles $media = null)` take the files of the media library the strip uses; an `Image` renders as `null` without them. Use `RenderStrips::run($page)`, which hands them over. A field class of the host that overrides `render()` adds the parameter.
- The package requires the PHP extension `dom` (`ext-dom`), which `symfony/html-sanitizer` already needed.
- Uploading through the CMS needs a `upload_max_filesize` and a `post_max_size` in PHP of at least `media.max_upload_kb` (25 MB by default); PHP itself stops at 2 MB when nothing is set, and the upload field then says that the server is the limit.
- The package requires the PHP extension `fileinfo` (`ext-fileinfo`) to read the type of an upload. Scaling photos needs GD with WebP support or Imagick, and `exif` to turn them upright; give PHP a `memory_limit` of at least 128 MB.
- The events of the content (`PageCreated`, `PageUpdated`, `PageMoved`, `PageDeleted`, `PageRestored`, `StripAdded`, `StripMoved`, `StripRemoved`, `StripUpdated`, `StripVisibilityChanged`, `DraftDiscarded` and `PagePublished`) implement `ShouldDispatchAfterCommit`: a listener runs once the transaction they are dispatched in commits, also a transaction of the host around an Action, and not at all when it rolls back.
- The side panel of the edit shell starts with the opbouw instead of "Klik een strook op de site om de inhoud te bewerken.", and hidden strips are chosen from the opbouw instead of a list of their own. "Strook n van m", in the panel and on the outlines in the frame, is the place of the strip in the opbouw: hidden strips and strips of a type the site no longer has count too.
- `RemoveStrip::run()` returns the removed `Strip` as it was stored (it returned nothing).
- `ListEditableStrips` lists every strip of the working copy, so the place of a strip in the list is the position the strip Actions take: a strip whose type left the catalogue is no longer left out but marked with `known: false`. `EditableStrip` has `known` and `summary` (`StripType::summary()`).
- `UpdateStrip` and `PublishPage` refuse strip values with the messages of the package in the language of the CMS (`StripType::messages()`, "Vul Kop in.") instead of the host's validation messages. A host that relied on its own `validation.*` lines for strips publishes the translations (`made-cms-package-lang`) and changes `strips.validation.*` there.

- `UpdateStrip::run($page, $stripId, $values)` merges the values with the stored values of the strip instead of replacing them: a field left out keeps its value instead of falling back to its default. To clear a field, pass it as `null` (or `[]` for a list); a host that relied on leaving fields out to reset them passes them explicitly. A list replaces the stored list, but an item with the `id` of a stored item keeps the fields it leaves out. The merged values are validated as a whole, so a field that was not passed can still be refused; `StripUpdated` is unchanged.
- Every item of an `Items` field has a fixed `id` (a uuid), given when the strip is stored by `AddStrip` or `UpdateStrip` and rendered as the first key of every item (`null` for an item stored without one). An item may no longer have a field named `id`: a strip type that has one renames it, or the catalogue throws `InvalidStripType`.

### Fixed

- Cleaning rich text no longer cuts it off at 65,535 bytes; the validation still allows at most 65,535 characters.
- Rich text nested deeper than 100 levels no longer crashes PHP when it is stored or rendered: markup beyond that depth keeps only its text.
- Changes to the draft made at the same time no longer get lost: two strips saved at once in the side panel, the opbouw moving or removing a strip while the panel saves another, two editors on one page. Every strip Action, `PublishPage` and `DiscardDraft` reads the page again in a transaction with its row locked (`ChangeDraft`), so the next change waits and starts from what the previous one stored; publishing and discarding see the draft as it was last stored. A page deleted in between throws `ModelNotFoundException` (404).
- A draft that no longer changes anything (a change undone, a strip hidden and shown again, a strip removed and put back) falls away: `draft_strips` is `null` again, the overview of the pages no longer shows a draft and the bar says "Geen wijzigingen". `UpdateStrip` then answers the strip as the published page holds it, with the ids of its items.
- `PublishPage` checks a field that a strip does not hold yet (a field its type got later) as its default, as the site renders it, instead of refusing it as empty. `UpdateStrip`, `RestoreStrip` and `PublishPage` check strip values in one place (`CheckStripValues`).

### Security

- A password login no longer tells by its speed whether an address has an account. An unknown address and an account without a password used to make a hash and check it, twice the work of a wrong password; from bcrypt cost 12 that took longer than the timebox of 400 ms could hide. Now every path checks exactly one hash: the stand-in is made once with the current hash settings and kept in the cache (again when the settings change).
- Login codes are stored as a keyed hash (HMAC-SHA256 with the app key) instead of the password hasher. Asking for a code and checking one now take the same short time for every address, so the timebox of 400 ms hides whether a code was made, also with a slower password hasher. A code asked for before this update no longer works; ask for a new one.
- A new login code only replaces the earlier code of the same browser. Someone who keeps asking for codes for an editor's address in another browser no longer makes the code and the mail link of that editor stop working.
- The login rate limits count an IPv6 address per /64, so one connection can no longer get past a limit by taking another address from its own block. IPv4 addresses (also written as IPv6) still count one by one.
- The login rate limits also count per typed address, whatever the ip address: 10 login codes and 50 passwords an hour. Changing ip addresses no longer gives unlimited guesses or an unlimited stream of mails to one address. A known and an unknown address get the same answer. A browser that logged in with the address before (the `made_cms_editor` cookie) counts on its own, so someone who exhausts the limit cannot lock the editor out on their own device. The password login has a limiter of its own, `made-cms-package.password`; `made-cms-package.login` now covers checking a code and the mail link only.
- The code from the authenticator app and the recovery codes are also limited per editor, whatever the ip address: 10 tries an hour, next to 5 a minute per ip address. Someone who knows the password can no longer guess the second factor from ever new ip addresses. An editor who runs into the limit can still log in with a code by mail.
- Rich text is also cleaned when it is rendered, not only when it is stored. HTML that reached `strips` or `draft_strips` another way (a seeder, an import, a field that used to be another type) and the `default()` of a `RichText` field no longer reach visitors or the edit mode with scripts, event attributes or `javascript:` links. A stored rich text that is not a string renders as `null`.
- `DescribeStrip` hands the side panel the values as the package stores them, so rich text that reached the database another way reaches the panel cleaned (an item without an id gets one there). The panel only shows rich text on the site in the frame as the markup it builds itself, also when "Ongedaan maken" puts a value back.
- The link button of a rich text field reads an address as the browser does: `javascript:` with a tab or line break in it is refused, and so is an address starting with `//` (another site that looks like an address on the site).
- A link in rich text to an address starting with `//` loses its address when it is stored and when it is rendered, so it can no longer lead to another site while it looks like an address on the site.
- A `Link`, and the link of a `Button`, renders only an address the validation accepts: one that reached the database another way (a seeder, an import), such as `javascript:alert(1)` or `//example.com`, renders as `null`, so a button disappears. The validation also refuses an address starting with `/\`, which the browser reads as another site. The side panel no longer shows such an address on the site in the frame while the editor types.
